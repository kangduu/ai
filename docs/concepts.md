# 前端 → AI：概念对照

把 AI 工程看成另一套 I/O 契约。左列是前端已经会的，右列是这边对应的输入和输出，不是另一套形而上学。

| 前端 | AI 工程 | 输入侧 | 输出侧 |
| --- | --- | --- | --- |
| 函数参数 / 组件 props | Prompt、Skill 触发上下文 | 用户原话、系统约束、工作区文件 | 按约定形状返回的文本或结构化数据 |
| 函数返回值 / 渲染结果 | 模型回复、tool call、最终产物 | — | 一次运行的可见结果；与可复用产物分开 |
| `fetch` / React Query | 模型 API 调用 | messages、tools、sampling 参数 | content、tool_calls、usage |
| TypeScript 类型 / Zod | JSON Schema、结构化输出 | schema + 用户话 | 可解析 JSON；失败则是原文 |
| 组件 / hooks 工具函数 | Skill | 触发语 + 局部上下文 | 该 Skill 的输出契约；产物是 `SKILL.md` |
| 状态机 / 副作用循环 | Agent | 目标 + 工具列表 | 轨迹（想了什么、调了什么）+ 终止结果 |
| 路由与中间件 | MCP / 工具协议 | 工具与资源描述 | 一次真实调用（读文件、打 API） |
| 搜索 + 列表页 | RAG | 切片后的知识 + 查询 | 命中片段 + 带引用回答 |
| 客户端缓存 / 归一化 store | Embedding、向量库 | 文本块 | 向量与近邻 |
| `AbortController` / SSE | 流式、取消、超时 | 产品约束、一次请求 | 分片 token、中止、超时错误 |
| 快照测试 / Playwright | Eval | 案例集 + 期望 | 分数、失败样本 |
| Sentry / 网络面板 | 可观测性 | 一次失败请求 | prompt 版本、工具调用、归因 |
| 鉴权、CSP、表单校验 | 护栏 | 含 PII、注入、越权的输入 | 拦截或过滤后的输出 |
| 设计系统 token | 模型与参数选型 | 同一任务、不同模型或 temperature | 质量 / 延迟 / 成本对照 |
| 编好 vs 生成时计算 | 微调 vs Prompt/RAG | 失败案例集 | 「还不用微调」或「值得微调」的判断 |
| 编排库 vs 自写 hooks | LangGraph 等 vs 自研 | 同一编排需求的一次真实尝试 | 选型理由，绑在案例上 |

## 读案例时怎么用这张表

打开 [Git 提交信息](../git/case.md) 可以对上：

- **props** = 用户说「帮我写提交信息」+ 暂存 diff
- **返回值** = 三种 commit 文案
- **组件实现** = [git/SKILL.md](../git/SKILL.md)（工作流和输出格式）
- **不要把一次返回值提交成组件源码**：文案是输出，Skill 才是产物

## 刻意不对齐的部分

- 模型输出非确定，不像纯函数。对照案例必须写运行条件（模型、参数、Skill），否则 I/O 无法复现。
- 「幻觉」更接近静默返回了错误数据，而不是抛错。要用 Eval 和引用，而不是只靠 try/catch。
- 上下文窗口有硬上限，不像无限滚动列表。输入要裁剪，这是上下文工程，不是产品经理多写两句需求。
