# 学习路径

阶段目标不是「读完一章概念」，而是：**能独立写出一组可复现的输入和输出**。先读案例，对照 I/O，再回看 [知识点地图](knowledge-map.md)。

## 现在就能做

1. 读 [Git 提交信息](../git/case.md)：看用户原话和 diff 如何变成三条 commit。
2. 打开产物 [git/SKILL.md](../git/SKILL.md)，区分「这一次的输出」和「下次还能用的约束」。
3. 用 [案例模板](case-template.md) 试着把你最近一次让 AI 干活的对话填进去。缺输出就先标「部分」，不要补假结果。

衡量：你能讲清这次任务的输入边界（哪些上下文必须给）和输出契约（怎样算合格）。

## 建议顺序

按层补案例，不必等一层「学完」再进下一层。每一层的完成标准都是至少一组真实 I/O。

| 阶段 | 去做什么 | 完成时你能交出来 |
| --- | --- | --- |
| 1. 模型基础 | 同一句话换 temperature 或模型，贴两次回复 | `llm/` 下一则对比案例 |
| 2. 交互与控制 | 保存一次 prompt 原文和回复；失败就保存改写前后 | `prompt/` 下一则案例 |
| 3. 知识与检索 | 对一份你自己的文档提问，贴命中片段和回答 | `rag/` 下一则案例 |
| 4. 行动与编排 | 已有 Git Skill；下一步记录一次带工具的 Agent 轨迹 | 新的 `agent/` 或 `mcp/` 案例 |
| 5. 工程化落地 | 给同一批输入打分，或接一次流式接口并保存网络日志 | `eval/` 或 `engineering/` 案例 |
| 6. 进阶选修 | 仅当 Prompt/RAG/Agent 有失败集时，再写「要不要微调」 | 判断案例，不是训练日志 |

前端对照（props ≈ 输入、返回值 ≈ 输出）见 [concepts.md](concepts.md)。待补案例名见 [roadmap.md](roadmap.md)。

## 不要怎么走

- 不要从「什么是 LLM」的长文开始。
- 不要为还没跑过的主题填写输出。
- 不要把单次回复当成产物；产物是下次还能用的 Skill / 模板 / 配置。
